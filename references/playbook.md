# 协作档与控长归档操作细节（playbook）

> SKILL.md 主文件只保留核心流程；本文件承载低频操作细节，按需加载。

## 1. 多人协作（协作档追加）

- **写权分区**：每个 L2 条目在 frontmatter `owner:`（选填）登记负责人；无 owner 的条目任何人可写，有 owner 的条目改前先过 owner。不锁谁写、锁内容规范——多人写不违规，内容不一致才是问题。
- **并发协调**：memcheck 的"重复主题"与"数字一致"检查就是并发写冲突的探测器——两人各自落盘后，任何一方跑 memcheck 即可发现对方写入造成的漂移；约定"每轮末尾必跑"天然形成冲突检测点。
- **提交纪律**：L2 目录建议纳入 git（条目/索引/归档都是纯文本，天然可 diff）；台账只追加 + 状态机在 git 历史里就是完整的决策审计链。L1 若无 git（如交付 docx），沿用"归档文件兜底"规则。
- **多人红线**：不得改动他人在条目中手写的内容（同"用户手工内容"红线）；发现疑似异常段落先问该段落作者再动。

## 2. 控长与归档

- 单条目 ≤ **8000 字**。超长拆三段（同一 scope）：

  | 文件 | 内容 | status | 进索引 |
  |---|---|---|---|
  | `<topic>.md` 主文件 | 现状快照 + 待办 + 关键技术 + 指针，≤1 屏 | active | 是 |
  | `<topic>-ledger.md` | 现行决策台账，一行一条带出处 | active | 是 |
  | `archive/<topic>-archive.md` | 历史轮次原文**逐字搬运不改写** | historical | 否 |

- **同一结论只在一处维护**：memcheck 重复检测（description 相似度 ≥80%、跨台账相同行）命中后合并或一处留指针。
- 拆分需**字符数守恒**（主文件 + 归档 = 原文，除 frontmatter）；若用脚本拆分，先核对脚本中的保留规则是否匹配当前文件结构——硬编码的前缀规则会把新快照误搬归档。
- 交付文档被新基线取代时：原文物理移出主文档进 `*-归档-YYYY-MM-DD.md`（无 git 的目录删除不可逆，归档兜底），主文档留墓碑行。
- 30 天未复核的 active 条目应复核或归档。

## 3. 升级流程（轻量档 → 三层）

```
python <skill目录>/scripts/init_memory.py --l2 <原L2> --l1 <新L1> --l3 <新L3> --upgrade
```

- 只补缺的层和配置项，**不覆盖、不搬移已有条目**；`--l3` 可多次传（跨应用每工具一个）。
- 升级后跑一次 memcheck 确认基线 ERROR=0。
- 迁移建议：原轻量档条目若已有 source（文件路径/commit），升级后可逐步把对应事实回填 L1 权威源文档，条目 source 改指 L1。

## 4. 性能约定

- memcheck 单进程纯文件扫描、每文件单次读缓存，万条以内秒级（实测 1000 文件 ~2s）。
- 每轮末尾跑一次；`--quiet` 单行输出适合快速门禁，完整报告用默认模式（写 MEMORY-REPORT.md）。
